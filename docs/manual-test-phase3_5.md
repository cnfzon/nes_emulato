# Phase 3.5 手動測試清單（音訊：要用耳朵與眼睛確認的項目）

自動化測試驗證了 APU 的暫存器邏輯與時序（blargg 的 APU／中斷測試 ROM）、輸出管線的數值（混音公式、
取樣數、音高的過零點次數）、環形緩衝區與動態速率控制（純數值模擬）、callback 的行為（prebuffer、
underrun、暫停、音量）。`nes-app --audio-selftest` 也在真實裝置上驗證過串流能開啟、緩衝區穩定。

**但這些都不等於「聽起來對」**：音高、節奏、音色、爆音／斷音，以及 GUI 上各控制項的實際行為，
**沒有人聽過、看過**。以下請用你自己合法取得的 ROM 手動確認（repo 裡沒有任何商業遊戲）。

## 準備

```bash
cargo build --release -p nes-app
target\release\nes-app.exe
```

- `File → Open ROM...` 載入；`View → Debugger` 開面板，切到 **APU** 分頁。
- 選單 **Audio**：靜音、主音量（預設 0.7）、裝置名稱與取樣率。
- 狀態列右側：`音訊：緩衝 NN ms | underrun N`。
- 挑一個**音樂明顯、你聽過原曲**的遊戲（例如有旋律、貝斯、鼓的關卡音樂）。若要測 DMC，需要真的用取樣的
  遊戲；不確定手上的遊戲有沒有用，就看 APU 分頁「DMC」的「輸出電平」有沒有在變動。
- 先確認耳機／喇叭音量不要開太大（第一次聽時主音量拉低）。
- **回報失敗時請附**：ROM 名稱、發生時間點、Debugger APU 分頁的截圖（尤其是緩衝進度條與 underrun）。

## A. 裝置與啟動

| # | 步驟 | 預期結果 |
|---|---|---|
| A1 | 啟動程式，開 `Audio` 選單 | 顯示「裝置：<你的預設輸出裝置>（NNNNN Hz）」；沒有錯誤提示 |
| A2 | （選做）先把系統預設輸出裝置停用或拔掉耳機／喇叭再啟動 | 程式**照常啟動、可載入 ROM 玩遊戲**；`Audio` 選單顯示黃色提示「音訊無法使用（…），將無聲執行」；狀態列顯示「音訊：無裝置（無聲）」；APU 分頁的緩衝區區塊顯示「沒有音訊裝置」；不會 panic 或當機 |
| A3 | 診斷指令（不開視窗、音量 0、不出聲）：`target\release\nes-app.exe --audio-selftest` | 印出裝置與 12 秒的緩衝統計：緩衝約 50 ms（我在自己的機器上量到 44.9–62.0 ms）、underrun 0、速率調整在 ±0.5% 以內 |

## B. 音樂的速度與音高

| # | 步驟 | 預期結果 |
|---|---|---|
| B1 | 載入遊戲，聽標題畫面或第一關音樂 | 旋律、貝斯、鼓都在，聽起來就是那首曲子（不是雜訊、不是全靜音、沒有明顯走音） |
| B2 | **速度**：與參考比較（另一個模擬器或錄音，同一段音樂、同一個起點）。一段循環音樂各數 3 次「一輪」的時間 | 與參考相同（差異在 1% 以內，人耳與碼錶都分辨不出來）。狀態列 FPS 應約 60.1 |
| B3 | **音高**：用手機調音器 App 對著喇叭，聽一個持續的三角波（貝斯）或方波（主旋律）長音；同時看 APU 分頁該聲道換算出的「頻率（Hz）」 | 調音器顯示的音名與頻率，和 APU 分頁的換算頻率相符（誤差 < 1%，約 17 cent 以內）；與原曲對照沒有走音 |
| B4 | 拖動 `Audio` 選單的音量滑桿（過程中音樂持續播放） | 音量平順變化，沒有「沙沙／拉鍊」雜音；拉到 0 完全無聲 |

## C. 長時間穩定（10 分鐘以上）

| # | 步驟 | 預期結果 |
|---|---|---|
| C1 | 載入一個會一直播音樂的遊戲，讓它跑 **10 分鐘以上**（可放著不操作），Debugger 開在 APU 分頁 | 全程沒有爆音（劈啪聲）、沒有斷音（短暫消失）、音高沒有慢慢漂移；**狀態列的 underrun 維持 0（或極少，且不在你聽到問題之外增加）** |
| C2 | 同時看 APU 分頁的緩衝進度條 | 穩定在目標（50 ms）附近，可接受範圍約 20–100 ms，**不會持續往上爬或往下掉**；「輸出取樣率」在裝置取樣率的 ±0.5% 內小幅變動；「累計丟棄取樣」維持 0 |
| C3 | 播放中拖動視窗、縮放視窗、開關 Debugger | 模擬與音樂不受 UI 影響地持續（UI 執行緒卡頓不會擋到 emu 與音訊執行緒）；允許極少數情況出現 1 次短暫的斷音，但**不應該永久累積延遲**（聲音與畫面差距不要越來越大） |
| C4 | 用工作管理員看 `nes-app` 的 CPU 使用率 | 沒有異常吃滿一個核心（emu 執行緒每毫秒醒來一次檢查，預期是低個位數 %） |

## D. 暫停與單步靜音

| # | 步驟 | 預期結果 |
|---|---|---|
| D1 | 音樂播放中按 Debugger 的「暫停」（或 Emulation → Pause） | 聲音在約 1/20 秒內**完全停止**，沒有殘留一小段舊音樂、沒有持續的嗡嗡聲 |
| D2 | 暫停中連按「單步一幀」「單步指令」數十次 | **完全靜音**（不會每按一次就發出一小段聲音） |
| D3 | 按「繼續」 | 音樂恢復；開頭沒有「補播一大段暫停前的舊音訊」的爆音（重新累積 50 ms 緩衝，所以會晚約 50 ms 才出聲，並有極短的淡入） |

## E. 各聲道獨立靜音

APU 分頁最上方有 5 個勾選框（Pulse 1、Pulse 2、Triangle、Noise、DMC；勾選 = 聽得到）。

| # | 步驟 | 預期結果 |
|---|---|---|
| E1 | 逐一取消勾選 Pulse 1、Pulse 2、Triangle、Noise | 取消哪個，音樂裡對應的部分就消失（方波主旋律／和聲、三角波貝斯、雜訊鼓／效果音）；其他聲道不受影響；重新勾選就回來 |
| E2 | 有用 DMC 的遊戲：取消勾選 DMC | DMC 的取樣（語音、鼓組等）消失。沒有用 DMC 的遊戲，此項跳過 |
| E3 | 全部取消勾選 | 完全靜音，但**遊戲照常執行**（畫面、按鍵、幀數不受影響；APU 分頁的暫存器與計數器仍在變動） |
| E4 | 靜音某聲道之後按 F5，再 F9 | 靜音設定**不受存讀檔影響**（它是輸出設定，不在存檔裡） |

## F. 存讀檔（F5／F9）後音樂正確接續

| # | 步驟 | 預期結果 |
|---|---|---|
| F1 | 音樂播放中按 F5；等幾秒（音樂進行到別處）；按 F9 | 音樂**回到按 F5 時的位置並接續播放**，沒有卡住的長音（stuck note）、沒有永久靜音；讀檔瞬間允許有一個很短的不連續（波形位置跳動） |
| F2 | 重複 F5／F9 十幾次，中間穿插暫停／繼續 | 每次都正確接續；underrun 不會因此明顯增加；沒有累積的延遲 |
| F3 | 載入另一個 ROM（音樂還在播放時） | 前一個遊戲的殘留聲音不會混進來；新遊戲的音樂正常 |
| F4 | 在音樂中按 F5，`File → Open ROM` 換另一個遊戲，按 F9 | 讀檔被拒絕並顯示錯誤（ROM 不符），目前的遊戲與音訊不受影響 |

## G. 需要注意的已知限制（不算失敗，但要知道）

- **沒有用真實遊戲驗證過音質**：APU 用 blargg 的測試 ROM 驗證過計時（`apu_test` 8/8、`blargg_apu` 11/11、
  `apu_reset` 6/6），沒有逐首比對過遊戲音樂。若聽到音色不對（例如某個 duty 或包絡線怪怪的），請回報
  遊戲與位置，並附 APU 分頁截圖。
- **DMC 暫停 CPU 固定 4 個 cycle、不模擬與 `$4016`／`$2007` 的衝突**（architecture.md §17.5）：用 DMC 的遊戲
  若手把輸入偶爾錯亂（搖桿讀取重複），這是第一個要懷疑的地方。
- **不處理音訊裝置熱拔除**：播放中拔掉耳機／切換預設裝置，cpal 會回報錯誤（只寫進 log），之後沒有聲音，
  需要重開程式。
- 只支援 NTSC 的時脈與週期表。
- `nes-core` 的 CPU 是 instruction-level：`cpu_interrupts_v2` 的 2–5 項預期失敗（NMI 劫持 BRK、IRQ 與 DMA
  的 cycle 對齊、分支對 IRQ 偵測的延遲）；少數依賴這些的遊戲可能有極細微的時序差異。
