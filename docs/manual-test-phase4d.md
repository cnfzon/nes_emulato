# Phase 4d 手動測試清單（連線大廳、統計疊加層、斷線、實機數據；兩台 Windows 電腦、區網）

自動化測試已經涵蓋了（細節見 [`architecture.md`](architecture.md) §21）：協定的語意防護（幀號過遠／過舊、冗餘輸入過多、
同一幀不同輸入、握手後的 Accept／Hello、陌生位址）、封包洪流下的記憶體上限、房間已滿（真實 UDP、第三個連線被拒絕、
原本兩端仍等價跑完）、統計的計算（虛擬時鐘）、CSV 寫出／讀回／`nes-test stats-summary`、emu 執行緒寫出統計 CSV 與結束摘要、
輸入欄位的檢查與疊加層文字（純資料邏輯）。

**但下列項目需要眼睛與手，沒有人在真實視窗與真實區網上確認過**：連線大廳的版面與中文字型、按鈕行為（複製、重新偵測、
取消、最近連線點選）、防火牆提示是否在 10 秒時出現、疊加層的外觀與折線、拔網路線時兩端的實際反應、摘要視窗、
Windows 防火牆、Wi-Fi／有線的真實延遲。**Desync 的醒目警告無法在 GUI 上觸發**（沒有辦法在執行中注入分歧；
它只由自動化測試與程式碼審視涵蓋），本清單不含。

**電腦 A 是房主（玩家 1）、電腦 B 是加入者（玩家 2）。電腦 C（或電腦 A 上的第二個 nes-app 視窗）用來測「房間已滿」。**

## 準備

```bash
cargo build --release -p nes-app -p nes-test     # 交付／量測用的 nes-app 請單獨建置（見 README）
target\release\nes-app.exe
```

- 各台電腦都要有**同一版**程式與**同一份** ROM（`nes-test info <rom>` 的 `rom_id` 必須相同）。用 Spacegulls
  （repo 根目錄的 `Spacegulls-1.1.nes`）。
- 鍵位（**每台都用「玩家 1」的按鍵配置**）：方向鍵、Z＝B、X＝A、Enter＝Start、右 Shift＝Select。
- 每場連線的檔案都在 **`nes-app.exe` 旁的 `netplay_replays\`**：
  `netplay-<Unix 秒>-p<1|2>-<ROM 前 16 字元>.replay` 與 `…-stats.csv`（每秒一筆的統計）。
- 回報失敗請附：步驟編號、截圖、`netplay_replays\` 的檔案。

## A. 連線大廳：本機 IP、建立房間、取消、防火牆提示（電腦 A）

| # | 步驟 | 預期結果 |
|---|---|---|
| A1 | 沒載入 ROM 時：`Netplay → 連線大廳…` | 大廳視窗「Netplay 連線大廳」開啟；黃字「請先載入 ROM…」；「建立房間／加入房間」兩個分頁的表單是灰的（不能操作） |
| A2 | 載入 Spacegulls，再看大廳頂端 | 「你的區網 IPv4：」後面是粗體位址（例如 `192.168.1.23`），旁邊有「複製」「重新偵測」；下方灰字說明「多張網卡／VPN 時可能不是對方所在網段的那個，不對請用 ipconfig」。**對照 `ipconfig` 的 IPv4 位址是否一致**（多張網卡時可能不同——這是已知限制，見 architecture.md §21.4）。拔掉網路線／關閉 Wi-Fi 後按「重新偵測」→ 黃字「偵測不到（沒有網路？）」，重新接上再按一次恢復 |
| A3 | 「建立房間」分頁：port 欄位清空或填 `0`、`70000`、`abc` 後按「建立房間」 | 表單內紅字說明（「port 必須是整數」／「必須在 1–65535 之間」）；不會建立房間、不會當機 |
| A4 | port 填 `7000`，看「請對方連到：」 | 顯示 `192.168.1.23:7000`（你的 IP＋port），有「複製」按鈕；按下去後貼到記事本應該是 `192.168.1.23:7000` |
| A5 | 模式選 rollback：看 Input delay 與預測視窗 K；改選 lockstep | rollback：預設 delay 1（上限 4）、K 預設 8（可調）；切到 lockstep：delay 預設 2（上限 8）、K 欄位變灰 |
| A6 | 按「建立房間」。**第一次**會跳出 Windows 防火牆提示 | 勾選「私人網路」→「允許存取」。之後大廳下方顯示轉圈圖示與「等待對手連線（UDP port 7000）… 已等待 N 秒」，N 每秒增加；兩個分頁的表單變灰（不能重複建立）；遊戲畫面停住（房主等人時不推進） |
| A7 | 什麼都不做，等待**滿 10 秒** | 「已等待 N 秒」超過 10 之後，大廳出現**黃字防火牆提示**：「已等待超過 10 秒仍然沒有人連進來。請檢查：① Windows 防火牆是否允許本程式使用 UDP port 7000 …② IP 與 port 是否相同 …③ 是否在同一個區域網路…」。**9 秒以前不應該出現** |
| A8 | 按大廳裡的「取消」 | 立即回到閒置：轉圈與提示消失、表單恢復可操作、沒有錯誤訊息；狀態列沒有 Netplay 資訊；`Emulation → Pause` 恢復可用 |
| A9 | 再建立一次房間，這次用 `Netplay` 選單的「取消」 | 同 A8 |
| A10 | 建立房間後**關閉大廳視窗**（右上 ✕），從 `Netplay → 連線大廳…` 重新開啟 | 房間仍在等待（狀態列藍字「[Netplay] 等待對手連線…」）；大廳還是顯示「等待對手連線…已等待 N 秒」，N 是**累計**的，沒有歸零 |
| A11 | 在電腦 A 的另一個 nes-app 視窗（同一台電腦）也建立 port `7000` 的房間 | 第二個視窗大廳顯示紅字「上一次嘗試失敗：無法在 port 7000 建立房間：…（這個 port 可能已被別的程式使用）」；第一個房間不受影響 |

## B. 加入房間、握手狀態、被拒絕、最近連線（電腦 B）

| # | 步驟 | 預期結果 |
|---|---|---|
| B1 | 電腦 B 載入**同一份** ROM；大廳「加入房間」分頁：欄位留空／填 `192.168.1.23`／`abc:7000`／`192.168.1.23:0`／`0.0.0.0:7000` 後按「連線」 | 各自有紅字說明（「請輸入…」「缺少 port…」「格式不正確…」「port 不能是 0」「IP 不能是 0.0.0.0…」）；不會送出連線 |
| B2 | 房主（A）**尚未**建立房間時，B 輸入 `192.168.1.23:7000` 按「連線」 | 轉圈與「正在連線到 192.168.1.23:7000…（n / 10 秒）」，n 每秒增加；表單變灰；有「取消」 |
| B3 | 等滿 10 秒 | 回到閒置；大廳顯示紅字「上一次嘗試失敗：連線逾時：對方沒有回應。請確認 IP 與 port 正確、房主已建立房間，且防火牆允許 UDP」；狀態列也有紅字。**沒有**跳出摘要視窗（沒連上過） |
| B4 | B 再按「連線」後，中途按「取消」 | 立即回到閒置，沒有錯誤訊息 |
| B5 | A 建立房間（等待中）；B 載入**不同的** ROM（或改過一個位元組的副本）後連線 | B 的大廳紅字「上一次嘗試失敗：連線被拒絕：ROM 不同：房主的 ROM 是 …，你的是 …。請雙方載入同一份 ROM 檔案」；**A 仍然在等待**（沒有被鎖住），A 的等待秒數繼續增加 |
| B6 | B 換回同一份 ROM，輸入正確的位址，按「連線」 | 通常 1 秒內連線：**兩端大廳自動關閉**；狀態列 `[Netplay rollback／lockstep] 已連線｜你是玩家 N｜ping … ms｜…`；雙方遊戲重新開機、畫面同步（同 4b／4c 清單的 B 節） |
| B7 | 中斷連線後，B 重新開大廳 →「加入房間」 | 「最近連線過（點一下填入）：」下面有一個按鈕 `192.168.1.23:7000`；點它，欄位自動填入。連線過多個位址時，最新的在最前面、最多 8 個、不重複；按「清除」後清單消失 |
| B8 | 連線失敗過的位址（B3）**不會**出現在最近連線清單，只有成功連上過的才會 | 確認 B3 那個錯誤位址不在清單裡 |
| B9 | 關掉 nes-app 再開 | 最近連線清單是空的（只存在記憶體，設定檔留到 Phase 5）——這是預期行為 |

## C. 房間已滿：第三個連線被拒絕，原本的對戰不受影響

先讓 A、B 連上、開始雙人遊玩（同 B6）。

| # | 步驟 | 預期結果 |
|---|---|---|
| C1 | 電腦 C（或 A 上的第二個 nes-app 視窗，**載入同一份 ROM**）：大廳「加入房間」，輸入 A 的 `IP:7000`，按「連線」 | 短暫「正在連線到…」後，C 的大廳紅字「上一次嘗試失敗：連線被拒絕：房間已滿：房主已經有對手了」 |
| C2 | 同時觀察 A、B | 兩台的遊戲**完全沒有受到干擾**：畫面繼續同步、沒有停頓、沒有彈出視窗、狀態列的 stall 次數沒有明顯增加；F3 疊加層的「已忽略封包」數字會增加（陌生位址的 Hello 被忽略，這是預期的） |
| C3 | C 連續再按「連線」約 10 次 | 每次都是「房間已滿」；A、B 仍不受影響 |
| C4 | A、B 結束連線（`中斷連線`）後，C 再連 A | A 已經回到單機，沒有房間，C 逾時（B3 的訊息）——確認舊連線結束後沒有殘留狀態；A 重新建立房間後 C 可以正常連上 |

## D. 統計疊加層（F3）

在 A、B 連線對戰中（分別做 rollback 與 lockstep 各一次）：

| # | 步驟 | 預期結果 |
|---|---|---|
| D1 | 按 **F3**（或 `Netplay → 統計疊加層（F3）`） | 遊戲畫面左上角出現**半透明黑底**的文字面板，遊戲畫面仍在後面前進（疊加層不擋鍵盤、不影響模擬；再按一次 F3 關閉） |
| D2 | rollback 模式：核對面板內容 | 依序有：`模式 rollback｜玩家 N｜input delay D 幀｜已確認 N 幀`、`ping N ms`、`rollback X.X 次/秒（累計 N）`、`重跑深度 平均 X.X／最大 N 幀`、`重跑耗時 平均 X.XX ms／最大 X.XX ms`、`幀數優勢 +X.X（對方回報 …）`、`預測準確率 XX.X%（對 N／錯 N）`、`stall N 次（X.XX 秒）`、`頻寬 ↑ … ↓ …`、`音訊 underrun N 次`；有陌生封包時多一行「已忽略封包 N」 |
| D3 | lockstep 模式：核對面板 | 同上，但 rollback 相關的幾行換成「lockstep：沒有預測與重跑（延遲高時會 stall）」，沒有第二條折線 |
| D4 | 看折線圖 | 有一條綠色 `ping` 折線（最新的在最右邊，圖上標目前值與 `max`）；rollback 模式還有一條黃色 `rollback/s`；剛連線時折線只有幾個點（靠右對齊），約 10 秒後填滿；下方有「最近 10 秒｜F3 關閉」 |
| D5 | 製造網路壓力：A 或 B 在做大檔案下載／串流，或 Wi-Fi 遠離路由器 | ping 折線明顯起伏；rollback 次數與重跑深度上升；預測準確率下降；stall（rollback 是預測視窗滿了、lockstep 是等對方輸入）增加。遊戲不會壞掉、雙方仍同步 |
| D6 | 對照下一節 CSV：疊加層的數字與該秒 CSV 的數字量級一致 | 例如 ping、每秒 rollback 次數、頻寬 |

## E. 斷線：對方正常離開 vs 拔掉網路線；本場摘要

| # | 步驟 | 預期結果 |
|---|---|---|
| E1 | 對戰進行 1 分鐘以上；**B 按 `Netplay → 中斷連線`** | **A 立即**（不到 1 秒）彈出「Netplay：連線結束」視窗，綠字「對方已中斷連線」；B 同樣彈出（綠字「你已中斷連線」）。兩個視窗都有「本場摘要（你是玩家 N）」：模式、時長（m:ss）與秒數、總幀數、ping 平均／最大、（rollback）rollback 次數／最大重跑深度／預測準確率、stall、傳送／接收位元組數、音訊 underrun 次數；下面有 **replay** 與 **統計 CSV** 的完整路徑。**兩台顯示的總幀數必須相同**（雙方取共同完成的幀數） |
| E2 | 關閉視窗後 | 已回到單機模式：遊戲畫面保持原狀、`Emulation → Pause` 可用、狀態列沒有 Netplay 資訊 |
| E3 | 重新連線，對戰約 30 秒後，**拔掉 B 的網路線**（或關掉 B 的 Wi-Fi） | B 的狀態列在約 **1.5 秒後**變成紅字「[Netplay …]…｜⚠ N.N 秒沒收到對方封包」（A 也一樣），N 隨時間增加；F3 疊加層最下面有紅色「⚠ 已 N.N 秒沒有收到對方的封包（超過 5 秒會中斷連線）」；遊戲會停住（lockstep 立刻、rollback 在預測視窗滿了之後） |
| E4 | 等到約 **5 秒** | 兩台都彈出「Netplay：連線中斷」視窗，黃字「連線中斷：超過 5 秒沒有收到對方的任何封包」，同樣有「本場摘要」與 replay／統計 CSV 路徑（斷線時雙方沒有交換幀數，各自存自己的長度；兩份 replay 可能差幾幀，但各自能通過 `replay verify`） |
| E5 | 接回網路線 | 已經回到單機；可以重新從大廳連線，不需要重開程式 |
| E6 | 關閉視窗 → 直接關掉 B 的 nes-app（連線中） | A 在約 0.5 秒內收到「對方已中斷連線」（B 關閉前會送出 Disconnect） |
| E7 | 強制結束 B 的行程（工作管理員「結束工作」）——**沒有機會送 Disconnect** | A 約 **5 秒**後顯示「連線中斷：超過 5 秒沒有收到對方的任何封包」（Windows 上對已關閉的 port 送封包會收到 ICMP，程式會略過它，仍靠逾時發現） |

## F. 實機數據收集（期末報告用）

**目標：兩台電腦分別以「有線」與「Wi-Fi」連線，lockstep 與 rollback 各玩 10 分鐘，共四場。**

| 場次 | 連線方式 | 模式 | 建議設定 |
|---|---|---|---|
| 1 | 有線（兩台都接網路線到同一台路由器） | lockstep | input delay 2 |
| 2 | 有線 | rollback | input delay 1、K 8 |
| 3 | Wi-Fi（兩台都用 Wi-Fi，同一個 AP） | lockstep | input delay 2 |
| 4 | Wi-Fi | rollback | input delay 1、K 8 |

每一場：

1. 記錄環境：日期、兩台電腦型號、網路型態（有線 100M/1G、Wi-Fi 2.4G/5G、離 AP 的距離）、路由器、雙方 nes-app 版本
   （`git rev-parse --short HEAD`）。
2. A 建立房間（選好模式與設定），B 加入。**F3 打開疊加層**，隨時觀察。
3. 認真玩 **10 分鐘**（雙人對打，不要暫停在選單；盡量維持一般的操作密度）。中途**不要**做其他耗網路的事，除非那就是這場的測試條件。
4. 時間到，**任一方按 `Netplay → 中斷連線`**；兩台都會顯示摘要視窗——把兩台的**摘要視窗截圖**存下來。
5. 把兩台的 `netplay_replays\` 整個複製出來，每場的檔案是：
   - `netplay-<秒>-p1-<ROM>.replay`／`…-p2-….replay`（雙方各一份）
   - `netplay-<秒>-p1-<ROM>-stats.csv`／`…-p2-…-stats.csv`（雙方各一份）
   場次與檔名的對照請自己記下來（或把檔案改名成 `wired-lockstep-p1-stats.csv` 這類好懂的名字——`stats-summary` 用檔名當表格的「檔案」欄）。

### F1. 用 `nes-test stats-summary` 把四份 CSV 整理成一張表

```bash
target\release\nes-test.exe stats-summary ^
  wired-lockstep-p1-stats.csv wired-rollback-p1-stats.csv ^
  wifi-lockstep-p1-stats.csv  wifi-rollback-p1-stats.csv
```

輸出是一張 Markdown 表：每個檔案的每個指標一列，欄位 `檔案 | 模式 | 秒數 | 指標 | 單位 | 樣本 | 平均 | 最小 | p50 | p95 | 最大`，
可以直接貼進報告。只看幾個指標：`--metrics ping_ms,fps,stalls,stall_ms,send_bytes_per_s,recv_bytes_per_s`。

| 預期結果 | 說明 |
|---|---|
| 每個檔案約 600 秒（樣本約 600） | 每秒一筆；`秒數` 欄是最後一筆的 `time_s` |
| lockstep 的檔案**沒有** `rollbacks`、`resim_*`、`frame_advantage`、`prediction_accuracy_pct` 列 | 這些欄位在 lockstep 是空的，不計入樣本 |
| `ping_ms`：有線通常個位數 ms，Wi-Fi 較大且 p95／最大明顯高於 p50 | 這是報告的重點：抖動 |
| `fps` 平均約 60；lockstep 的 stall 多時 `fps` 的最小值與 p5 會低於 60 | rollback 的 `fps` 是「已確認幀」的速率，較接近 60 |
| 欄位單位：`stalls`、`rollbacks`、`audio_underruns` 是**這一秒內的次數**；`stall_ms` 是這一秒內的毫秒數；頻寬是位元組／秒（UDP payload，不含 28 位元組的標頭） | 單位在表格的「單位」欄 |

`stats-summary` 的錯誤處理（也請確認一次）：對不存在的檔案或亂寫的 CSV 執行，會印出檔名（與行號）與原因、結束碼 2；
`--metrics` 打錯名字會列出所有合法的指標名稱。

### F2. 結束後：雙方 replay 雜湊值相同，且都通過 replay verify

每一場都做（正常結束、雙方有交換幀數時）：

```powershell
Get-FileHash -Algorithm SHA256 netplay-<秒>-p1-<ROM>.replay, netplay-<秒>-p2-<ROM>.replay
```

| 預期 | 說明 |
|---|---|
| 兩份 replay 的 SHA256 **完全相同** | 雙方取共同完成的幀數，位元組完全一致（4b／4c 已用自動化測試證明；這裡是實機確認）。**檔名裡的 `p1`／`p2` 與時間戳不同是預期的，內容必須相同** |
